We need to change the CUDA-side genome storage model for a generational GA so that it uses reusable arenas instead of a full previous-generation buffer plus a full next-generation buffer, while also supporting growth of the model’s output embedding vocabulary over time.

At the moment, the naive design is to hold the previous generation in one contiguous device buffer and write the next generation into another contiguous device buffer of the same size. That is simple, but it effectively doubles VRAM requirements for organism storage during breeding. We want to reduce that memory pressure.

The new design should treat a generation not as an owning contiguous buffer of organisms, but as a membership list pointing into shared storage arenas. An organism should no longer be identified by “its position in the generation buffer”. Instead, a generation should be represented by arrays of slot IDs that refer to reusable storage slots in one or more device-resident arenas.

This remains a generational GA. Parent selection for a generation must still be based only on the original current generation. We are not switching to a steady-state GA. We are only changing how storage is managed while a full next generation is being produced.

The genome should be split into two parts.

The first part is the main model body. This is everything whose shape stays fixed across vocabulary growth events: hidden layers, encoder weights, policy-head components that are not directly the expandable output embedding tail, and any other fixed-size per-organism data. This main body should live in a fixed-slot arena in device memory. Every slot in this arena has the same size. A live organism owns exactly one body slot. This arena should support reuse: once a parent organism has no remaining assigned matings and is no longer needed, its body slot can be returned to a free-slot pool and later reused for a child.

The second part is the output embedding tail. This is the only part of the genome that grows when new output embeddings are injected into the action space. The tail must not be stored as a monolithic contiguous extension of the main body, because that would force whole-organism resizing when vocabulary grows. Instead, the tail should be stored separately in its own arena using fixed-size chunk slots. Vocabulary growth happens in consistent increments, so each increment should correspond to one constant-size tail chunk. An organism therefore owns one body slot plus zero or more tail chunk slots. Tail chunks are not contiguous with the body in memory, but each individual chunk is contiguous and fixed-size.

Generations should therefore be represented by two logical membership structures: one for body slot IDs and one for tail chunk IDs or equivalent per-organism tail references. The exact layout can be flattened arrays if that is easier on CUDA. All organisms in a given generation should conform to the same vocabulary schema: same number of tail chunks, same chunk size, same mapping from output action index to chunk index and offset within chunk. That schema can change between generations when new output embeddings are injected, but the main body slot size must remain unchanged.

The recombination pipeline should work like this. At the start of a generation, evaluate fitness and compute the full parent/mating plan for the entire next generation. Count how many times each current-generation parent will be used. That gives a remaining-use counter for each parent. Then produce children according to that precomputed plan. For each child, read parent body slots and parent tail chunks, allocate a body slot for the child from the body arena, allocate the required tail chunks for the child from the tail arena, recombine and mutate into those destinations, and record the resulting slot IDs in the next-generation membership arrays. After each mating event, decrement the remaining-use counters of the participating parents. When a parent’s remaining-use count reaches zero, reclaim its body slot and all of its owned tail chunks back into their respective free-slot pools. This lets storage be reused during a generational breeding pass without changing GA semantics.

We want the normal case to avoid a full double-buffered population. Instead of needing two full population-sized organism buffers, we want one shared reusable body arena and one shared reusable tail arena. The initial target is to size these arenas to around 1.4 times the single-generation requirement rather than 2.0 times, with the understanding that this is a heuristic starting point and must be instrumented.

Vocabulary growth should be handled by adding tail chunks, not by resizing whole organisms. When the output vocabulary expands, the global generation schema advances, meaning new children in the next generation will have an extra tail chunk or chunks corresponding to the newly injected vocabulary range. Existing tail chunks continue to represent earlier vocabulary ranges. Core body slots do not move and do not change size because of vocabulary growth. Output embedding lookup and inference code must therefore stop assuming one monolithic contiguous tail and instead use the generation schema to map an action index to a chunk index and in-chunk offset.

Please do not implement a general variable-sized allocator, linked structures, arbitrary fragmented per-organism heaps, or a switch to steady-state evolution. Keep the design explicit and regular: fixed-size body slots, fixed-size tail chunk slots, index-based addressing, explicit free-slot stacks or queues, explicit per-parent remaining-use counters, and explicit schema/version information for the output vocabulary structure.

We also want an explicit emergency fallback path if the arena is exhausted. This can use host-backed or managed memory, but only as a noisy degraded-mode safety valve. It must never be the normal design assumption. If overflow happens, log it clearly and record enough instrumentation to see why it happened.

Please build this incrementally. First, refactor organism representation so that body and output tail are separate, with body slots and tail chunk references instead of one monolithic blob. Second, introduce the body arena and tail chunk arena with slot-ID-based addressing, even if the first version does not yet reclaim slots aggressively. Third, add precomputed mating plans and remaining-use counters so parents can be retired safely. Fourth, add actual body-slot and tail-chunk reuse during breeding. Fifth, add schema-aware tail growth so new vocabulary increments allocate new tail chunks rather than triggering whole-organism migration. Finally, add explicit noisy overflow handling and instrumentation.

Instrumentation is required. Track at least live body slot count, peak body slot count, live tail chunk count, peak tail chunk count, free-slot low-water marks for both arenas, spill or overflow events, and schema-epoch transitions. We need to be able to see whether the 1.4x sizing assumption is working in practice.

The end state we want is this: a generational CUDA GA where each organism consists of one fixed-size main-body slot plus a set of fixed-size output-tail chunk slots; current and next generations are membership arrays of slot IDs into shared arenas; parent slots and tail chunks are reclaimed once that parent has no remaining assigned matings; vocabulary growth appends new tail chunks instead of resizing whole organisms; and the whole system uses substantially less VRAM than a naive full double-buffered organism layout.
